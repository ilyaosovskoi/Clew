# Clew — анализ пробелов и идей для развития

*Составлено по итогам разбора исходного кода Clew v2.0.1 и сравнения с Claude Code / OpenAI Codex CLI.*

---

## 1. Чего не хватает (по функциям, найдено в коде)

| Пробел | Что есть у конкурентов | Что нашлось в Clew |
|---|---|---|
| **Hook-система на уровне тула** | PreToolUse/PostToolUse/UserPromptSubmit хуки для аудита и enforcement-политик | Только plugin-система для роутов/провайдеров/JS-CSS — не может перехватывать конкретные tool calls |
| **Checkpoint / rewind** | У Claude Code — откат состояния диалога и файлов | Не найдено (`checkpoint`, `rewind` — 0 совпадений в коде) |
| **GitHub-нативная автоматизация** | `@codex implement issue`, GitHub Action `claude -p` на каждый PR | `git_service.py` — только локальный `status/diff/stage/commit/branch/log`, без PR/issue automation |
| **Облачное / фоновое выполнение** | Codex: закинул задачу в контейнер, закрыл ноутбук | Агент всегда работает на локальной машине пользователя в реальном времени |
| **MCP только как клиент** | — | Clew подключается к внешним MCP-серверам, но сам MCP-сервером быть не может |
| **Тонкое тестовое покрытие** | Миллионы реальных сессий обкатки | ~43 200 строк исходников, ~2 960 строк тестов (≈7%), 9 test-файлов на 128 модулей — тонковато для security-critical кода (sandbox, guardian) |

## 2. Что у Clew уже сильное (и чего нет у конкурентов)

- **Second Opinion** — кросс-вендорное ревью рискованных вызовов другой моделью/провайдером. Ни у Claude Code, ни у Codex такого нет — они заперты в одном вендоре.
- **Office Worker** — нативная работа с .docx/.xlsx/.pptx прямо из агента, без шелл-аутов.
- **Progressive tool disclosure** (`select_tools`) — компактный каталог тулов с дозагрузкой по требованию.
- **SwarmManager** — параллельные субагенты с git-worktree/checkout изоляцией (аналог Agent Teams).
- **Rust sandbox** (Landlock/Seatbelt) — необратимое применение при старте процесса, плюс многослойный `command_policy.py` (user → project → session).
- **Мультипровайдерность + локальные модели** — 16 провайдеров + 200+ через OpenRouter + офлайн через Ollama/LM Studio. Единственный из трёх вариантов, где работа без единого байта в облаке архитектурно возможна.

## 3. Идеи новых фич — то, чего нет ни у кого, но растёт из архитектуры Clew

Эти идеи специально выбраны так, чтобы использовать то, что у Clew уже есть в фундаменте (мультипровайдерность + локальность + zero telemetry), а не добавлять случайную фичу ради галочки — Claude Code и Codex физически не могут это повторить, будучи single-vendor SaaS.

### 3.1 Консенсус нескольких провайдеров вместо одного ответа
Развитие уже существующего Second Opinion: на сложную/спорную задачу агент генерирует решение параллельно 2–3 разными провайдерами, показывает diff между подходами и объясняет, в чём и почему они расходятся. Не "проверка после факта", а несколько независимых решений одной задачи с сопоставлением — полезно для архитектурных развилок.

### 3.2 Криптографически подписанный офлайн аудит-трейл
Развитие уже существующего zero telemetry + ChaCha20-хранения ключей: каждый diff/решение агента подписывается локальным ключом с таймстампом — получается неопровержимый журнал "что изменил ИИ, когда и на основе какого промпта", полностью на диске пользователя. Ниша, где облачные SaaS-агенты не могут конкурировать в принципе (регулируемые отрасли: медицина, финтех, госсектор).

### 3.3 Автоматический learning loop из реальных провалов
Развитие уже существующей инфраструктуры `Loop_Engineering_Guide.md` / `learnings/`, но без ручного заполнения: агент сам детектирует, что diff откатили или тест, объявленный зелёным, упал в CI позже — и автоматически создаёт запись в `learnings/`, которая инжектится в промпт при похожих задачах в этом же репозитории. Замкнутый цикл самообучения на уровне конкретного проекта — у конкурентов такого нет.

## 4. Открытые риски (честно, без прикрас)

- Темп разработки сейчас высокий (1 месяц от первой беты), но это одна точка данных, а не подтверждённый долгосрочный тренд.
- Тестовое покрытие не поспевает за сложностью security-critical подсистем — один заметный инцидент на раннем этапе доверия может стоить дороже, чем аналогичный баг у крупного вендора (см. кейс Codex и SSD-логов).
- Соло/маленькая команда против конкурентов с большим штатом — это не гонка по количеству фич, а вопрос bus factor и покрытия огромной матрицы провайдер×ОС×конфигурация.
- Стратегически выгоднее не догонять конкурентов по общей широте функций, а закрепиться в нише, куда сама архитектура толкает: приватность/офлайн/аудит и мультипровайдерный консенсус.
