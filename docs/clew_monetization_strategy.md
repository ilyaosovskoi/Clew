# Как монетизировать Heavy Code / Office при открытом исходном коде

Контекст из кода (важно, т.к. монетизация должна встраиваться в то, что уже
заложено, а не изобретаться с нуля):

- В `quota.py` уже есть деление на секции `general | heavy_code | office` с
  дневными лимитами (`DEFAULT_DAILY_LIMITS`): `heavy_code` — 10/день,
  `office` — пока `0` (не enforced, т.е. фактически безлимит, потому что
  секция ещё не выпущена). Есть готовый комментарий в коде: *"Future
  versions will add paid tiers (>10/day)"* — то есть авторы уже думали в эту
  сторону, просто не достроили.
- `office_worker.py` — самописный (без обёртки над сторонним агентским
  кодом) движок для .docx/.xlsx/.pptx поверх `python-docx`/`openpyxl`/
  `python-pptx`. Полностью локальный, без внешних зависимостей на API.
- `agent_runtime.py` — `heavy_code` уже поднимает `max_iterations`,
  `RUN_TIMEOUT`, `MAX_OUTPUT` относительно `general`.

Открытый код — это код (весь `clew/` целиком можно склонировать и
собрать самому). Продавать нужно не сам код, а то, что дорого/неудобно
воспроизводить самостоятельно: **инфраструктуру, данные, время и доверие**.
Ниже — конкретные направления именно для Heavy Code и Office, без
изменения лицензии на сам движок.

---

## 1. Managed quota / hosted providers — самое естественное продолжение уже существующей механики

Сейчас `heavy_code` лимитирован 10 запросами в день **локально**, без какой-либо
серверной части — это легко обойти, отредактировав JSON на диске (`quota.py`
сам предупреждает об этом в комментариях про file-locking против гонки
процессов, но не защищает от редактирования файла руками).

**Идея:** open-core модель.
- Ядро (агент, tool-use loop, office_worker, весь `clew/`) остаётся открытым и
  работает с BYO API-ключом (bring your own key) — пользователь платит
  провайдеру (Anthropic/OpenAI/etc.) напрямую, Clew с этого не берёт денег.
- Платный слой — **Clew Cloud**: managed-прокси к LLM-провайдерам с более
  высокими лимитами `heavy_code`/`office` (>10/день), без необходимости
  заводить свой ключ. Технически это готовый переход от текущего
  `DEFAULT_DAILY_LIMITS` (локальный enforcement) к серверному — тот же
  `section`/`exhausted()` API, только backend квоты живёт не в
  `~/.clew/quota_history.jsonl`, а в облаке Clew, привязанный к аккаунту.
- Открытый код при этом ничего не теряет: любой может достать свой API-ключ и
  пользоваться без лимитов вообще, просто это требует своей настройки
  (типичная модель GitLab CE/EE, Supabase, n8n — движок открыт, облако платное).

## 2. Heavy Code — продавать не код, а вычислительное окружение

`agent_runtime.py` для `heavy_code` уже поднимает `RUN_TIMEOUT`/`MAX_OUTPUT`/
`max_iterations` — то есть Heavy Code это по сути "агенту нужно дольше и
больше гонять код/тесты". Собственно исполнение кода (`execute_command`,
`run_code`) сейчас идёт локально на машине пользователя.

**Идея:** платные **изолированные sandbox-раннеры в облаке** (container-per-run,
GPU/более мощный CPU, предустановленные тулчейны — Node/Rust/Docker-in-Docker,
что тяжело поднять на слабом ноутбуке). Пользователь остаётся с открытым
клиентом Clew, но по кнопке "Run in Cloud Sandbox" код/тесты уходят выполняться
на managed-инфраструктуре Anthropic-совместимого рантайма. Это прямой аналог
того, как GitHub продаёт Actions runners поверх открытого Git, или как
Codespaces продаёт вычислительные мощности поверх открытого VS Code.

Дополнительно в эту же корзину:
- **Heavy Code teams-фичи**: общий лимит/биллинг на команду, аудит-лог кто и
  сколько потратил (это естественно ложится поверх уже существующего
  `token_tracker.py`/`quota.py` — просто агрегировать по организации, а не
  по локальному пользователю).
- **Приоритетные модели/скорость**: тот же интерфейс, но с приоритетным
  доступом к более мощным/быстрым моделям в периоды нагрузки — классическая
  для API-based продуктов вещь.

## 3. Office Worker — вертикальные шаблоны и интеграции, а не сам движок

`office_worker.py` уже целиком открыт и работает локально (python-docx/
openpyxl/python-pptx). Продавать сам факт "может делать .docx" бессмысленно —
любой скопирует модуль. Монетизировать стоит то, что вокруг:

- **Библиотека корпоративных шаблонов**: брендированные шаблоны договоров,
  презентаций, финансовых моделей с уже настроенным стилем/логотипом/
  формулами — это контент, не код, и его дорого поддерживать в актуальном
  состоянии (юридические шаблоны меняются, брендбуки обновляются). Продаётся
  подпиской, отдельно от движка.
- **Интеграция с реальными Office-аккаунтами**: сейчас `office_worker.py`
  работает только с локальными файлами. Платная фича — прямая запись/чтение
  в SharePoint/Google Drive/OneDrive/Google Sheets API с OAuth, синхронизация
  версий, совместное редактирование. Это требует hosted OAuth-инфраструктуры,
  токен-стораджа и поддержки API квот сторонних сервисов — ровно то, что
  тяжело/невыгодно поддерживать для одного человека локально, но легко
  продать как SaaS-надстройку.
- **Валидация и compliance-проверки** поверх сгенерированных документов
  (например: "проверь, что в контракте нет пунктов, конфликтующих с GDPR",
  "приведи презентацию к корпоративному брендбуку") — тонкий платный слой
  поверх открытого генератора, монетизирующий экспертизу/датасет правил, а
  не сам код.

## 4. Общие для обеих секций модели монетизации поверх открытого кода

- **Managed cloud-инстанс** (аналог self-hosted vs cloud у GitLab/Supabase):
  тот же открытый Clew, но развёрнутый и обслуживаемый Anthropic/партнёром —
  платишь за то, что не надо самому поднимать сервер, настраивать бэкапы,
  обновлять зависимости.
- **Enterprise-функции поверх открытого ядра** — SSO/SAML, ролевой доступ,
  централизованная политика `command_policy.py` (whitelist команд) на уровне
  организации, аудит-логи для комплаенса. Это классический open-core паттерн:
  ядро бесплатно, "Enterprise" слой продаётся отдельно и физически не
  распространяется с открытым репозиторием (или распространяется, но требует
  лицензионного ключа для активации — как у GitLab EE).
- **Marketplace для slash-команд/суб-агентов**: раз в проекте уже есть
  инфраструктура `.claude/commands/*.md` (см. предыдущий аудит) — можно
  построить публичный каталог платных/бесплатных пресетов команд под Heavy
  Code (например, готовый пайплайн "аудит security", "миграция на TypeScript
  strict") и под Office ("сгенерируй квартальный отчёт из CSV"). Автор
  команды получает процент от продаж — модель как у плагинов JetBrains/VS Code.
- **Support/SLA-контракты** — платная поддержка, приоритетные багфиксы,
  выделенный канал связи для компаний, которые используют Heavy Code в
  проде и не хотят полагаться на комьюнити-багтрекер.

## Итоговая рекомендация по приоритету

1. **Managed quota/API-прокси (п.1)** — дешевле всего внедрить, напрямую
   продолжает уже существующий код `quota.py`/`section`, не требует новой
   инфраструктуры кроме биллинга и серверного счётчика вместо локального.
2. **Office-интеграции с реальными облачными аккаунтами (п.3, второй пункт)** —
   самое явное "то, что открытый код сам по себе не даёт" (OAuth,
   инфраструктура, поддержка чужих API), при этом ценность для пользователя
   огромна (перестать руками скачивать/загружать файлы).
3. **Cloud sandbox-раннеры для Heavy Code (п.2)** — дороже в реализации
   (нужна настоящая контейнерная инфраструктура), но это самый прямой ответ
   на вопрос "почему кто-то заплатит, если код открыт" — потому что платит
   не за код, а за железо и изоляцию.
4. **Enterprise/marketplace/support (п.4)** — долгосрочные, но более
   капиталоёмкие с точки зрения продаж/юридической части направления.
